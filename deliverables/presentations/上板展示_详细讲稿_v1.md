## 1. 开场：上板运行的整体成果

前面已经介绍了 MiniRISC-16 CPU 的结构和指令执行过程。接下来我介绍这颗 CPU 放到 FPGA 开发板上之后，实际运行了哪些程序，以及程序如何与板上的外设交互。

目前我们在同一套 Runtime 硬件系统上实现了三个项目：流水灯、2048 和贪吃蛇。它们共用 CPU、程序存储器、数据存储器、UART、定时器和其他外设。切换项目时，我们通过串口上传不同的机器码程序，不需要重新设计 CPU 或重新生成一套游戏专用硬件。

这里有一个容易混淆的地方：统一选择菜单运行在电脑端。电脑端菜单负责选择程序、调用 UART Loader 上传程序，并打开对应的显示终端。板上的 CPU 在一个时刻执行其中一个程序，并不同时执行三个游戏，也不负责绘制电脑端菜单。

## 2. UART：程序上传与运行交互（PPT 合为一页）

这一页用一张模式对照图讲完整个 UART 的用途，口头讲解可分为“上传程序”和“运行时交互”两段：

| 模式 | SW7 | UART 接管者 | 电脑发送 | 板端发送 | CPU 状态 |
|---|---:|---|---|---|---|
| 程序加载 | 1 | UART Loader | 机器码程序 | 上传应答 | 保持复位 |
| 程序运行 | 0 | CPU 的 UART 外设 | 按键命令 | 运行状态帧 | 执行程序 |

### 2.1 程序如何上传、切换和启动

三个项目能复用同一套硬件，关键在于程序存储器是可写的。它的容量为 1K×16 位，每个地址存一条 16 位机器码。我们先把汇编程序转换为机器码镜像，再通过 UART Loader 将镜像写入程序存储器。

上板操作中，SW7 是加载与运行模式开关。SW7 为 1 时，CPU 保持复位，Loader 接收电脑发送的机器码；上传完成后，把 SW7 拨回 0，CPU 解除复位，从程序地址 `0x000` 开始执行刚上传的程序。

顶层 RTL 中，与这个过程直接相关的代码是：

```verilog
wire cpu_rst = rst | load_mode;

assign uart_tx = load_mode ? loader_uart_tx : cpu_uart_tx;
```

第一行把加载模式并入 CPU 复位条件，所以写程序期间 CPU 不会一边运行、一边读取正在修改的指令。第二行选择 UART 的发送端：加载模式时发送 Loader 的应答；运行模式时发送 CPU 程序的输出。两种模式共用开发板上的同一组串口引脚。

程序存储器的读写路径也很直观：

```verilog
always @(posedge clk)
    if (loader_we) memory[loader_addr] <= loader_wdata;

assign instruction = memory[cpu_addr];
```

`loader_we` 为 1 时，Loader 按 `loader_addr` 写入一条 16 位机器码；CPU 运行时则按 `cpu_addr` 取出指令。这里的 `instruction` 最终送到 CPU 核心执行。

UART 每次传送一个 8 位字节，而程序字是 16 位，因此 Loader 把高、低两个字节拼成一个程序字。以下为 `program_loader.v` 中的连续代码：

```verilog
ST_DATA_L: begin
    program_addr <= word_index[9:0];
    program_wdata <= {data_high, rx_data};
    program_we <= 1;
    checksum <= checksum + {data_high, rx_data};
    word_index <= word_index + 1'b1;
    if (word_index + 1'b1 == word_count)
        state <= ST_SUM_H;
    else
        state <= ST_DATA_H;
end
```

`data_high` 是上一个收到的高字节，`rx_data` 是当前收到的低字节。两者拼接后写到程序存储器，同时累加校验和。接收完全部程序字后，Loader 检查电脑发送的校验和，并回传成功或失败应答。

[现场操作：SW7 拨到 1，观察数码管 `10AD`；电脑端选择项目并等待 `UPLOAD PASS`；SW7 拨回 0，展示程序运行。切换下一项目时重复这一过程。]

### 2.2 运行时电脑与 CPU 如何交换数据

UART 在当前系统中有两种用途。第一种是刚才介绍的程序上传。第二种是程序运行时的输入输出：电脑把按键发给 CPU，CPU 把游戏状态发给电脑，电脑端终端根据状态数据绘制画面。

开发板上的 CP2103 是现成的 USB 转串口芯片，负责电脑 USB 与 UART 信号之间的转换。FPGA 内部的接收模块 `uart_rx`、发送模块 `uart_tx` 和 CPU 访问接口 `uart_port` 是工程中的 Verilog 实现。串口参数是 115200 波特率、8 位数据、无校验、1 位停止位，也就是 115200、8N1。

接收器的核心是四状态状态机：

```verilog
localparam IDLE = 2'd0, START = 2'd1,
           DATA = 2'd2, STOP = 2'd3;
```

空闲状态等待起始位；检测到起始位后，在位周期的中间确认它，再依次采样 8 个数据位；最后检查停止位。如果帧有效，就把收到的字节放到 `data` 输出，并产生一个 `valid` 脉冲。`uart_rx` 还用两级寄存器同步外部输入，降低异步输入直接进入状态机的风险。

发送器则在 CPU 写入一个字节后，将起始位、8 个数据位和停止位按位送出：

```verilog
assign ready = ~busy;

if (write_enable) begin
    shift <= {1'b1, write_data, 1'b0};
    tx <= 1'b0;
    busy <= 1'b1;
end
```

`ready` 表示可以接收下一个待发送字节。发送器忙时，CPU 程序需要等待，避免连续写入导致数据丢失。

CPU 访问 UART 时不需要直接控制起始位和停止位，而是使用输入输出端口。`0x10` 是 UART 数据端口，读这个地址取得收到的字节，写这个地址发送字节；`0x11` 是状态端口。地址译码 RTL 如下：

```verilog
assign uart_data_read = read_enable && address == 8'h10;
assign uart_data_write = write_enable && address == 8'h10;
```

`uart_port` 里的状态寄存器组织为：

```verilog
assign status_rdata = {13'h0000, overrun, tx_ready, rx_valid};
```

其中最低位 `rx_valid` 表示已有一个接收字节，下一位 `tx_ready` 表示发送器空闲，`overrun` 表示前一个字节尚未读取时又收到新字节。

CPU 程序接收按键时，先读取状态，再用按位与检查最低位：

```asm
    INP  R0, 0x11
    MOVI R1, 0x01
    AND  R0, R1
    CMP  R0, R1
    JZ   READ_KEY
```

如果 `rx_valid` 为 1，程序再通过 `INP R0, 0x10` 取出按键。发送状态帧时则检查 `tx_ready` 对应的 `0x02` 位，准备好之后执行 `OUP 0x10, R0`。这就是 CPU 指令与 UART 外设之间的连接。

电脑端的作用是发送控制字节、接收状态帧和绘制界面。2048 的合并规则、贪吃蛇的碰撞判断以及流水灯的下一灯位置，均由 FPGA 上的程序计算。

## 3. 流水灯：从位置运算到 LED 输出

第一个程序是流水灯。现象是板上的 LED0 到 LED7 单灯循环移动，两端自动回绕。方向键或 `A`、`D` 可以改变方向；`SW1～SW0` 可以选择四档速度；`SW2` 可以暂停。

流水灯程序的状态保存在 RAM 中：`0x20` 存当前位置，`0x21` 存方向，`0x22` 存帧序号，`0x23` 存拨码状态，`0x24` 存最近按键，`0x25` 存当前 8 位图案。CPU 在主循环中读取按键、拨码和定时器，只有定时器事件到来时才更新LED位置。

以向右移动为例，汇编代码是：

```asm
MOVE_RIGHT:
    MOVI R3, 0x20
    LDR  R0, R3
    MOVI R1, 0x07
    CMP  R0, R1
    JZ   RIGHT_WRAP
    ADDI R0, 0x01
    STR  R3, R0
    JUMP RENDER_PATTERN
```

CPU先从RAM的`0x20`读出当前位置；如果已经是7，就跳到回绕代码把位置设为0；否则加1并写回RAM。向左移动同理，只是执行减1，并在位置0时回绕到位置7。

新位置算好后，CPU生成LED图案：

```asm
    MOVI R1, 0x01
PATTERN_LOOP:
    ...
    ADDR R1, R1
    ...
PATTERN_READY:
    OUP  0x30, R1
```

这段是讲解性节选，省略号处是比较位置和循环计数的代码。R1从`0000 0001`开始，每次执行`ADDR R1,R1`就加倍一次，等效于左移一位。假如当前位置为3，加倍三次得到`0000 1000`，然后通过 `OUP 0x30,R1`写入LED端口。

LED外设RTL本身只是一个寄存器：

```verilog
always @(posedge clk) begin
    if (rst) led <= 8'h00;
    else if (write_enable) led <= write_data;
end
```

地址译码模块在CPU向`0x30`输出时产生`write_enable`。LED寄存器保存CPU写来的低8位，并直接驱动板上LED。这个模块并不自行计算“下一盏灯”，移动和回绕由汇编程序完成。

定时器提供节拍：

```verilog
if (!pause && !tick_pending) begin
    if (counter >= selected_cycles - 1) begin
        counter <= 32'd0;
        if (half_tick) begin
            half_tick <= 1'b0;
            tick_pending <= 1'b1;
        end else begin
            half_tick <= 1'b1;
        end
    end
end
```

这里每经过两个计数周期才产生一次`tick_pending`事件。CPU读取定时器端口`0x12`后清除该事件；暂停时计数停止。由于定时器会保持待处理事件，CPU在串口发送状态帧较慢时也不会立刻积累多个移动动作。

流水灯还会把图案、位置、方向、速度、拨码和最近按键组成12字节状态帧，经UART发送给电脑终端。终端展示的是板上程序计算后的结果。

[现场操作：展示位置移动；按`A`/`D`反向；改变`SW1～SW0`；用`SW2`暂停；指向终端中的图案与位置。]

## 4. 2048：CPU 怎样完成一次移动

第二个程序是2048。它有4×4棋盘，支持方向键移动、相同数字合并、随机生成新方块、计分、胜利判断和无路可走判断。

16个棋盘格保存在连续RAM地址`0x40～0x4F`。每格保存的是2的指数，而非直接保存显示数字：0为空格，1表示2，2表示4，3表示8，依此类推。这种表示使合并操作很简单：两个相同指数的方块合并时，把指数加1即可。

例如一行实际数字为`2、空、2、4`，RAM保存的是`1、0、1、2`。向左移动后，前两个2合并，结果是`4、4、空、空`，RAM中的指数变为`2、2、0、0`。

CPU收到方向键后，把棋盘按移动方向拆成4条逻辑行。程序先清空`0x50～0x53`这4个临时格子，再逐个扫描原始行。读到零就跳过；读到非零方块，就与临时缓冲区最后一个有效方块比较。如果两者相同，而且该方块在本次移动中没有合并过，就执行合并；否则把它追加到临时行的下一个位置。

合并分支的实际汇编核心为：

```asm
MOVE_MERGE:
    ...
    LDR  R1, R3
    ADDI R1, 0x01
    STR  R3, R1
    ...
```

这里也是讲解性节选。`LDR`取出上一个方块的指数，`ADDI`使指数加1，`STR`将合并结果写回临时行。程序另外保存一个“刚刚合并过”的标记，保证一个方块在一次移动中最多合并一次。例如`2、2、2、2`左移应得到`4、4`。

分数计算同样由CPU完成。程序从1开始重复执行寄存器自加，得到合并后方块对应的2的幂，再把这个值加到RAM中的16位分数。处理完4条逻辑行后，CPU按原棋盘的地址顺序写回，并比较新旧数值，判断这一步是否真正改变了棋盘。只有有效移动才会生成新方块。

随机值由 FPGA 内的8位LFSR提供：

```verilog
wire feedback = value[7] ^ value[5] ^ value[4] ^ value[3];

if (advance)
    value <= {value[6:0], feedback};
```

CPU通过`INP 0x13`读取随机值，用它选择0到15号格子。如果选到已占用位置就重试；连续16次未找到空格则顺序扫描。选定位置后，程序根据另一个随机值生成指数1或2，即数字2或4。游戏结束判断则先检查有没有空格；满盘时再检查横向或纵向是否仍存在一对可合并方块。

最后，CPU把棋盘16格、分数、状态和帧序号等组织为27字节状态帧发送给电脑。电脑终端把指数转成可见的数字并绘制彩色棋盘。棋盘压缩、合并、计分和生成规则都在板上的程序里。

[现场操作：移动一次，指出原棋盘、合并结果和分数变化；再尝试一次无效移动，说明不会因此生成新方块。]

## 5. 贪吃蛇：坐标、碰撞和蛇身更新

第三个程序是贪吃蛇。当前逻辑地图是16列、8行，共128格。方向键控制蛇移动，吃到食物后增长、计分并逐步加速；撞到边界、障碍墙或蛇身后游戏结束。拨码开关还可以在重新开始时选择不同地图。

首先是坐标表示。程序用一个数表示二维位置：`位置 = 行号×16 + 列号`。因为每行正好16格，向上是减`0x10`，向下是加`0x10`，向左是减1，向右是加1。CPU在移动前先判断是否已经到边界。

以向右移动为例：

```asm
MOVE_RIGHT:
    MOVR R3, R0
    MOVI R2, 0x0F
    AND  R3, R2
    CMP  R3, R2
    JZ   GAME_OVER
    ADDI R0, 0x01
```

R0是当前蛇头位置。`AND 0x0F`得到列号。如果列号已经是15，继续向右就越界，于是条件跳转到游戏结束；否则将位置加1。

地图存放在RAM中，从地址`0x04`开始连续占128个格子。值为0表示空格，`0xFF`表示墙，其他非零值表示蛇身的剩余寿命。每次移动时，CPU遍历128格，对非墙且非零的蛇身值减1。减到0的尾部格子成为空格，然后在新蛇头位置写入当前蛇长。

对应的汇编循环是：

```asm
DECAY_LOOP:
    LDR  R0, R3
    MOVI R1, 0xFF
    CMP  R0, R1
    JZ   DECAY_NEXT
    MOVI R1, 0x00
    CMP  R0, R1
    JZ   DECAY_NEXT
    MOVI R1, 0x01
    SUB  R0, R1
    STR  R3, R0
```

`LDR`读出当前格，两个`CMP/JZ`分别跳过墙和空格，`SUB`把蛇身寿命减1，`STR`写回。循环地址从`0x04`增加到`0x83`，总共处理128个格子。这段代码很适合回答“蛇到底是怎么被CPU移动的”。

接着，CPU读取新蛇头位置对应的格子。若仍为非零，就发生墙或蛇身碰撞；若为空，则继续比较它是否与食物位置相同。吃到食物时，程序增加蛇长与分数，再寻找下一个食物位置。

食物生成过程先通过`INP 0x13`读取LFSR随机数，取低7位得到0到127号地图格，再加`0x04`转换为RAM地址。若该格被占用就重试；最多随机尝试16次，随后顺序扫描128格。这样地图接近占满时，程序仍能在有限步骤内找到空格或确认无空格。

每轮更新完成后，CPU把128个地图格以及状态、分数、等级、帧序号和异或校验组成140字节帧，通过UART发送给电脑。终端收到后绘制墙、蛇身、蛇头和食物。地图和蛇身状态已经由CPU计算完成，终端负责把数值转换成可见画面。

[现场操作：改变方向；吃一颗食物并指出蛇长和得分变化；展示暂停、地图选择和一次碰撞结束。]

## 6. 收尾总结

这三个项目虽然现象不同，但运行过程有共同点：CPU先读取按键、拨码或定时事件，执行汇编程序中的判断和运算，更新RAM状态，再通过LED或UART输出。

流水灯体现的是定时输入、位置更新和LED输出。2048增加了棋盘数组处理、合并、计分和随机生成。贪吃蛇增加了坐标计算、地图遍历、碰撞判断和较长的数据帧传输。三个程序使用相同的Runtime硬件，通过UART Loader切换程序镜像。

以上就是这部分的上板运行效果及其实现原理。

## 7. 老师追问时的备答

### 统一菜单是否运行在 CPU 上？

当前统一菜单是电脑端脚本。它选择程序、上传镜像并打开对应终端。SW7切回运行模式后，板上的CPU执行已上传的程序。

### UART 是否全部由我们设计？

开发板自带CP2103 USB转串口芯片。FPGA内部的UART收发模块、接收缓冲、状态寄存器和CPU端口译码由工程中的Verilog实现。说“FPGA内部UART逻辑自行实现”是准确的。

### 电脑端显示游戏，怎样区分计算和绘图？

电脑发送按键并显示状态帧；板上的程序维护棋盘、地图、分数、位置等状态。2048合并与贪吃蛇碰撞更新发生在CPU执行的汇编代码里。终端根据CPU发来的状态值绘制画面。

### 定时器是不是直接驱动 LED 或蛇？

定时器只产生待处理的节拍标志。CPU读取端口`0x12`后才进行一次状态更新，再写LED或者发送UART。定时器不保存游戏规则。

### 2048 没有乘法和移位指令，如何完成合并和计分？

方块以指数表示，合并只需指数加1。需要计算分数时，程序从1开始重复自加得到2的幂。行列地址中的乘4也能通过连续自加得到。

### 贪吃蛇为什么每步遍历128格？

蛇身以剩余寿命表示。每走一步，旧蛇身都要减1，使尾巴在适当时间消失。当前地图规模为128格，CPU循环逐格处理可以完成这一更新。

### 串口发送画面较慢，定时事件会不会积压？

定时器用一个`tick_pending`位保存待处理事件。这个位还没有被CPU读取清除时，计数器暂停推进，所以不会连续积压多个节拍，避免发送完一帧后立刻补做多次移动。

## 8. 现场演示顺序与代码展示建议

建议演示顺序：统一菜单和SW7切换 → 流水灯 → 2048 → 贪吃蛇。每次切换前先进入加载模式，上传成功后再回到运行模式。

正文展示的源码建议控制在三组：

1. UART页合并展示顶层`load_mode`切换和`0x10/0x11`端口；程序存储器写入与`INP/OUP`汇编只选一处重点讲，其余由口头补充。
2. 流水灯的位置更新与`OUP 0x30`，说明LED现象如何产生。
3. 2048的合并分支、贪吃蛇的`DECAY_LOOP`，说明复杂规则如何由CPU执行。
